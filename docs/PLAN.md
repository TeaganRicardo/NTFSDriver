# NTFSDriver 开发与验收计划

计划日期：2026-10-12。需求依据：[PRD v1.0](PRD.md)。目标环境为 Apple Silicon / macOS 27.0.1。

本计划优先保证**像 macOS 原生支持 NTFS**的可观察结果：一次安装和系统授权后，物理 NTFS 磁盘经 Disk Arbitration 自动被选中，在 `/Volumes` 呈现为可由 Finder、磁盘工具和标准文件 API 管理的真实本地卷，具有正确的只读/读写属性及系统退出行为。使用 `libntfs-3g` 作为唯一文件系统引擎；以 [xntfs 原生 FSKit 实现](NATIVE_EXPERIENCE_REFERENCE.md)为技术主标杆，以 Paragon 的用户体验为验收标杆。**不引入新 KEXT、FUSE 虚拟卷替身、网络共享、常驻抢挂载 daemon 或降低启动安全等级的方案。**

维护者不购买付费 Apple Developer 账号。因此 `com.apple.developer.fskit.fsmodule` 授权签名与后续免费发布是**前置交付阻断**，不能隐藏在项目的最后一步。无可用授权时，允许继续离线源码、模拟卷和公开接口研究，但不宣称 M2 或完整产品可交付；详见 [签名限制](SIGNING.md)。

## 首要成功标准：原生卷体验

| 验收动作 | 必须观察到的结果 | 不合格的近似实现 |
| --- | --- | --- |
| 仅首次安装/授权 | 用户完成 macOS 要求的扩展启用后，无需每日启动 app、脚本、终端或重复授权 | 常驻菜单栏/守护进程抢占系统自动挂载 |
| 插入洁净 NTFS **真实 USB 设备** | 系统选择我们的 FSKit 模块，映射到**原始** `/dev/diskNsM` / DADisk，卷名、容量、UUID、物理介质身份合理，`/Volumes/<Volume>` 自动出现 | 新建合成虚拟 disk，或将 NTFS 内容呈现为普通文件夹 |
| macOS 原生操作 | Finder 侧栏可用；磁盘工具能够检查卷身份；`diskutil info`、`statfs`、Foundation 属性一致；Finder/NSWorkspace/diskutil 可正常卸载及推出 | 仅 `ls`/POSIX 读取成功，或只有 `umount` 能结束虚拟卷 |
| 数据文件操作 | 普通读写、保存替换、创建删除、重命名、打开文件生命周期、同步、并发、元数据与 Windows 往返均正确 | 只用一份可丢弃镜像做 create/read/write 演示 |
| 卷异常与系统安全 | dirty/休眠/日志风险及 I/O 异常拒写或安全只读；SIP 和 Full Security 不变，无第三方 KEXT | 静默 RECOVER、重置日志、清 dirty、降启动安全 |
| 最终发行 | 有**经合法授权签名并可分发**的 FSKit 扩展；干净机器安装/卸载/升级通过 | ad hoc 仅能编译、复用不能修改的第三方签名、收费成品当作我们的免费发行 |

这些是验收条件，不意味着本项目目前已经通过。强制破坏性测试只使用可丢弃镜像或明确标记的专用测试磁盘。

### G0-R：能直接复用就不重复实现（与签名 G0 并行）

在继续扩展代码前，先对照 xntfs 的 `ntfs3g/bridge/`、`ntfs3gVolume.swift`、`ntfs3gFileSystem.swift`、测试与本项目 `CNTFSBridge`、`NTFSReadOnly`、`NTFSFSKit` 建立**逐文件功能/缺口/许可/测试矩阵**。一次性选择以下路径，不维持两套并行的 NTFS 数据层：

- **A（优先）复用成熟 FSKit 适配层**：若逐文件授权与本项目最终发行许可证确实兼容，直接以 xntfs 的已验证 bridge/volume/测试为基础（必要时以 fork/代码导入形式保留版权历史），将 NTFSDriver 已验证的安全默认、设备保护和测试补充进去；对重合旧模块只保留一个实现。现有代码的许可证若必须调整，先验证所有权利并获得权利人许可；**不得自行将 GPLv3 文件改标 GPLv2**。
- **B（授权不兼容的回退）**：保留本项目 GPL-3.0-or-later 源码，复用公开 FSKit/NTFS-3G API 与兼容性测试思路，独立完成**最薄**直接 FSKit 桥接；不用未经授权的代码移植，也不重新写 MFT/NTFS 引擎。
- **两条路共同前提**：保留固定、已验哈希的 `libntfs-3g`；输出迁移成本、数据路径数量、许可证来源与每项回归证据。签名 G0 不成立时，代码仍可完成离线验收，但不得把 fork/源码导入当作可安装产品。

### M2 最小垂直切片：实现顺序

1. **冻结基线**：保留已通过验证的 `libntfs-3g 2026.9.28`、`CNTFSBridge`、`NTFSReadOnly` 和现有 FSKit 卷；审查 xntfs 公开接口和测试设计，**不直接复制许可兼容性未确认的源码**。
2. **真实设备 I/O 与卷身份**：让 FSKit `loadResource` 接收真正的 `FSBlockDeviceResource`，全程只读；对齐、短读、撤销/关闭、边界及单位换算用现有代码与单测扩展。原物理 BSD/DA 身份需端到端保留，不创建合成卷。
3. **系统发现与仲裁**：参考 xntfs `Info.plist` 的媒体声明，核对 NTFS 分区类型/分区表与 `FSProbeOrder`；明确与内置只读 NTFS 模块竞争的结果，避免不相关介质误认。生产启用应在 G0 与受控专用介质验证后。
4. **系统集成硬验收**：保存同一会话的扩展选择、`diskutil info -plist`、DADisk 描述、`mount`/`statfs`、Foundation 属性、Finder 侧栏及 Finder/NSWorkspace/diskutil 退出结果。失败时先修系统接入，不要扩写业务逻辑。
5. **安全状态机**：在所有可能引入可写 backend 的路径上重验 clean/dirty、hibernation、journal、I/O 错误、显式 readonly 与后续激活；系统向上层报告的只读属性必须与底层一致。写入直到 M3 明确启用。
6. **小型管理入口**：只在安装授权失败/诊断或用户主动调用时出现；系统自动挂载不依赖 GUI 进程或定时轮询。

### 复用优先与明确不做

- **复用**：NTFS 引擎及设备操作 API、已有只读安全桥、Apple FSKit/DA、官方元数据协议、xntfs 和 NTFSKit 的公开行为/测试清单；必要且许可证兼容时再考虑移植成熟代码。
- **不做**：从零解析 MFT、重新实现压缩/NTFS 日志/ACL、第二套并行 NTFS 引擎；优先级不高的管理 UI；为弥补签名缺失构造模拟网络共享或“fake native”挂载。
- **macFUSE**：保留已有成功的只读实验和验证脚本作为旁证；5.4.0 的合成卷、系统只读属性和卸载问题已阻断正式接入。除非上游**正式公开**可完成真实块设备关联、自动仲裁、只读和标准推出的新接口与有签名版本，否则不继续扩写 FUSE 业务层。
- **REA**：优先用开源代码及第一方系统 API 解决问题；需要确认安装在本机、合法授权的闭源组件接口时才做定向静态/动态逆向，保留 Evidence，**不把反编译作为绕过 FSKit 授权方式**。

## M1 已交付范围

M1 的诊断输入为从 NTFS 分区起始扇区开始的原始普通文件镜像。工具以只读文件描述符读取有界头部，拒绝设备节点、目录、FIFO 和末级符号链接。完整磁盘的分区表、DMG 容器和真实磁盘访问不属于本批范围。

检查 OEM 标识、引导扇区结束标记、保留字段、扇区与簇大小、卷长度、MFT 与镜像 MFT 位置、记录大小编码及整数溢出。这里只能确认引导结构，不能确认完整 NTFS 文件系统健康。诊断始终报告写入被拒绝，Dirty Flag、休眠状态及元数据一致性仍为未知。

FSKit 适配器只探测块设备头部。它最多返回“已识别”，不返回“可用”；加载、检查、格式化全部拒绝。本批不安装或注册扩展，因此不会改变当前磁盘的挂载流程。

## 引擎接入门禁

M2 已固定 NTFS-3G 2026.9.28 提交并引入未修改的引擎源码，项目代码采用 GPL-3.0-or-later；接入结论见 [引擎审查](ENGINE_AUDIT.md)，来源与许可见 [第三方说明](../THIRD_PARTY.md)。以下门禁继续适用，完整写入安全与系统集成仍未验收：

- 固定上游提交并保存来源、许可证与构建选项。
- 确认只读打开、挂载与检查路径不会进行日志恢复、Dirty Flag 修改、休眠文件删除或其他隐式写入。
- 在设备 I/O 层强制拒绝写入，并在测试中记录所有写请求。
- 明确 FSKit 直接 I/O 与元数据缓存的使用策略，处理短读、短写与同步失败。
- 先完成只读本地卷，再启用经过验证的写入路径。

## M2 已完成范围和仍缺失的系统闭环

现有只读普通文件镜像已能枚举卷信息、分页目录、按精确名称查找、读取和哈希；设备桥拒绝写模式及写调用，并使用 READONLY/FORENSIC。FSKit 27 适配层具备只读活动状态、item 生命周期与设备读；宿主 `.app` + `.appex` 可 ad hoc 构建，但自有扩展因缺少授权配置文件无法启动。当前 `FSMediaTypes` 为空，不会接管 NTFS 设备。

macFUSE 5.4.0 已签名后端让本项目普通进程在 `/Volumes` 读取一个本地虚拟卷，但磁盘工具识别的是 4KiB 合成设备，Foundation 报 writable，`diskutil` 和标准 App 退出未通过；详见 [实验记录](MACFUSE_EXPERIMENT.md)。该成功不等同于原始 NTFS 分区的系统卷身份。**后续不将解决 macFUSE 虚拟卷的 UI 表象作为完成 M2 的捷径。**

目前技术主标杆变更为 [xntfs 的 direct FSKit 物理卷流程](NATIVE_EXPERIENCE_REFERENCE.md)。其公开的 macOS 27 镜像和附加分区验证可借鉴，但真实物理 USB 自动选择、本项目签名和免费分发都必须独立实测/落实。工作必须按上文 G0 → M2 → M3 执行，未满足之前保持原先只读工具而不声明日用驱动。

## 测试与证据

自动测试先使用合成引导头验证解析边界和拒绝路径；合成头不是完整 NTFS 卷，也不能替代引擎或挂载测试。随后使用 `mkntfs` 创建的可丢弃分区镜像进行只读和读写集成验证。

每次集成验收记录 macOS/SDK 版本、源码提交、扩展版本、引擎版本、卷特性、测试设备或镜像、挂载属性、文件哈希与退出结果。实机测试覆盖 Finder、磁盘工具、标准文件访问、重复插拔、重启、休眠和 Windows 交替使用。

所有破坏性测试仅在明确标记的专用测试盘或可丢弃镜像上执行。性能先建立同设备基准，再确定阈值。未完成的实机验收保持待验证状态。
